# Deep review and workbench redesign — 2026-08-12

This document is the engineering and curriculum handoff for the v12 practice-workbench redesign. It records what was wrong, what changed, which claims are deliberately limited, and what the next contributor should verify before extending the system.

## Outcome

The main practice loop is now:

1. **Hear Movement** — follow one practical, voice-led triad route through the complete ii–V–I pivot cycle.
2. **Song Map** — choose a common progression by musical job, then see both Roman numerals and chord symbols in the selected home.
3. **Ear Checks** — identify either dromos colour or the complete home/family/change map, with known-home and blind modes kept explicit.
4. **Triads & Comp** — keep one string set and neck area while the complete selected progression is globally voice-led.
5. **Solo Road** — connect the established map to phrase routes and chord-tone arrivals.

The interface no longer uses a narrow global inspector on the right. It uses a curriculum rail plus one workbench: page controls and the musical explanation sit together, shared setup is one horizontal bar, advanced sound/display options are collapsed, and transport remains reachable at the bottom.

## Audit findings and fixes

### 1. The cycle showed legal pitches, not a practical execution

**Finding:** Hear Movement drew a generic four-note fretboard search for each seventh chord. Each result could be playable in isolation, but the app did not preserve a string set, register, or hand route across the 18-chord loop. It therefore taught the theoretical cycle and an unrelated sequence of grips at the same time.

**Fix:** `Triads.pathThrough()` now uses dynamic programming across the complete progression. It:

- stays on one adjacent three-string set;
- respects an overlapping open, middle, upper, or whole-neck practice zone;
- prices every individual voice movement, large leaps, shape span, and register drift;
- can include the final-to-first transition in its objective;
- exposes route metrics for tests and learner feedback.

Hear Movement defaults to the top three strings and the middle zone. The display distinguishes the **full heard chord** (for example Dm7) from its **played triad skeleton** (Dm), and names the omitted seventh as colour rather than pretending it is present.

This follows the practical inversion sequence described by [Berklee's triad-inversion lesson](https://online.berklee.edu/takenote/guitar-chords-101-triad-inversions-up-the-fretboard/) and the conservation-of-motion principle in [Voice Leading for Guitar](https://online.berklee.edu/takenote/voice-leading-for-guitar/). The app does not reproduce either source's notation or exercises.

### 2. Triads & Comp used a greedy next-shape search

**Finding:** the old router chose the locally cheapest next shape. A locally good inversion could force an avoidable jump later, and the default could switch string sets. "All shapes" made the highlighted route hard to understand.

**Fix:** Triads & Comp uses the same complete-route optimizer, gives the player explicit string-set and neck-area controls, and filters faint alternatives to the selected working area. Readout text now explains that the highlighted object is a route decision, not an exhaustive chord dictionary.

### 3. Song Map was a flat list

**Finding:** progressions were technically named but did not answer the learner's first question: "What job does this progression do in a song?"

**Fix:** the progression bank now declares categories such as Cadences, Home loops, Turnarounds, Modal motion, and Song endings. Each choice shows its stable Roman-numeral map and its current transposed chord symbols together.

### 4. Ear Checks mixed reference, answer, and scoring controls

**Finding:** the shared reference-tonic control remained visible in the full-map drill even when the map had a different answer. That could give an incorrect home reference. The selection stages also looked like one configuration block.

**Fix:** Colour ID and Home + Changes are numbered activities. The full-map drill owns its home control and can explicitly play the known home chord; blind mode disables that button. Home, family, and progression are separate decision cards, and checking remains an explicit commit. Natural minor, harmonic minor, strict equal-tempered Ousak, and Hijaz remain separate coherent answer families.

### 5. Tablet audio could clip and lose pitch definition

**Finding:** every chord voice used approximately the same high gain regardless of chord size, while bass, click, and percussion fed the same unrestricted master. The Karplus–Strong recurrence also produced pitch-dependent peak levels. This could hard-clip on iPad speakers and make a noisy attack dominate the fundamental.

**Fix:** the new speaker-safe chain adds:

- per-buffer peak normalization;
- polyphony-aware per-voice gain;
- high-pass cleanup and restrained instrument-specific tone filtering;
- a quiet, short fundamental body oscillator for pitch definition on small speakers;
- a `DynamicsCompressorNode` and conservative output stage;
- lower bass/percussion/click levels;
- explicit one-sample audio priming on the first real pointer/touch release.

The compressor uses the standardized Web Audio node documented in the [Web Audio API specification](https://www.w3.org/TR/webaudio-1.1/#DynamicsCompressorNode). This is still a synthesized practice voice, not a claim to reproduce a recorded bouzouki, laouto, or guitar.

### 6. Offline caching could mix two releases

**Finding:** the service worker was cache-first forever. During verification, the new HTML loaded beside an older cached `app.js`, visibly reproducing the user's report that a deployed update was missing.

**Fix:** v12 uses network-first same-origin app requests with cache as offline fallback. All CSS and JavaScript shell URLs are release-versioned so even an already-installed older worker cannot combine releases.

## Deliberate limits and next work

1. **Listen on a physical iPad Pro.** Browser automation proves lifecycle and clipping safeguards, but it cannot judge the actual device speakers. Compare guitar, tetrachordo bouzouki, and laouto at several volume levels. Adjust only the instrument profiles and master output—not the musical route—to preserve test separation.
2. **Build a player-reviewed voicing corpus.** The algorithmic triads are pitch- and hand-consistent, but idiomatic full-chord vocabulary should be reviewed by strong players per instrument and stored with source/provenance notes.
3. **Add guide-tone and shell routes as a separate texture.** Do not silently call a root/3rd/7th shell a triad. A future texture control should keep the displayed and sounded notes identical.
4. **Continue modular extraction.** `js/app.js` still coordinates too many view controllers. The pure music engines are now separated well enough to extract `cycle-view.js`, `song-map-view.js`, and `ear-view.js` incrementally behind the existing DOM contract.
5. **Keep dromos claims bounded.** Current Ousak and Hijaz maps are explicit equal-tempered teaching collections. Do not present them as a complete account of makam intonation, seira, regional practice, or every historical harmonization.

## Change-safety rules for the next contributor

- Update `docs/REQUIREMENTS.md` whenever a music invariant changes.
- Add a pure self-test before changing a chord bank, scale collection, voicing objective, or ear answer.
- Keep visual notes and sounded notes identical unless the UI explicitly labels heard harmony versus played skeleton.
- Run `npm run check`, `npm test`, one iPad-width browser pass, and one phone-width pass before pushing.
- Do not remove the asset version or restore cache-first navigation.
